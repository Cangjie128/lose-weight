## 当前决策

最终部署只使用用户自己的 Oracle Cloud 服务器，不使用 Supabase。当前交付是本地产品原型，不是可直接部署的生产后端。不会在本轮登录服务器、安装服务、修改生产数据库或切换域名。

新版本默认 `NEXT_PUBLIC_DATA_BACKEND=local`。仅配置旧 Supabase URL/Key 不会触发连接。仓库中的 Supabase 模块、迁移和测试暂时保留，用于旧数据兼容与回归，不作为最终生产方案；只有显式选择 `legacy-supabase` 才可进入旧适配器，且它不支持新增计划持久化。新本地模式不会调用旧云端认证或付费识别。

## 服务组成

浏览器连接同源 HTTPS 的 Nginx/Caddy；反向代理到 Next.js Node API。PostgreSQL 只监听本机或私有网络；独立持久卷保存餐食文件。应用、PostgreSQL、图片卷和密钥备份分开管理。数据库和文件路径不能暴露给浏览器。Docker Compose 或 systemd 的选择留待服务器环境核对后确定。

原型数据使用完整 `AppData` 快照，包含个人资料、历史记录、每周计划和执行调整。`shiguang.snapshots` 的 JSONB 保留该结构，并用递增 `revision` 做 compare-and-swap，防止另一设备静默覆盖。必要时可在同一数据库内逐步拆分记录表与索引，不引入第二个主数据库。

计划 ID 以周一日期稳定定位；任务 ID 以原始日期和任务类型定位。重新排期保存在独立执行调整中，不改写原始任务 ID；照片和实际记录有 `plan_task_id` 关联。模型估算与计划粗估通过营养来源和备注区分。

## 账号和权限设计

- 账号由自己的数据库管理，不依赖第三方邮箱认证。注册、登录、退出、密码重置及限流都在新服务端实现后才能开放。
- 密码保存经过校准的 Argon2id 哈希；若目标运行环境不适合，使用符合 OWASP 参数要求的 scrypt。每个密码独立随机盐；不保存明文或可逆密码。
- 登录生成高熵随机会话，数据库只保存会话摘要、到期时间与撤销状态。浏览器使用 `Secure`、`HttpOnly`、`SameSite` cookie；不把会话或服务密钥放入 localStorage、日志或 ZIP。
- 写入需同源校验和 CSRF 防护，登录需逐账户和逐来源限流。错误信息不枚举邮箱，退出和改密可撤销会话。
- API 只相信认证后的 principal，不接受客户端指定其他用户 ID。每次数据库事务使用验证过的用户 UUID 执行 `SET LOCAL app.owner_id`，避免连接池串号。
- 业务数据库角色不能是超级用户、表所有者或 `BYPASSRLS`；认证网关仅获需要的账号/会话权限。数据库 RLS 之外仍有服务层授权，不能把 RLS 当作万能防护。

这是后端实施要求，不是本轮已完成的认证功能。发布前必须覆盖密码重置、会话固定/撤销、并发登录、CSRF、跨账户读写及审计测试。

## 服务器照片设计

- 例：`/srv/shiguang/data/images/<owner-id>/<sha256>.jpg`，目录不位于 `public/` 或 Nginx 静态站点下。
- 数据库只存 ID、相对路径、大小、类型、SHA-256 和关联，不存图片二进制或 Base64。
- 上传先校验大小、文件签名和尺寸，再写入受限暂存目录；认证完成后由服务器构造路径，做规范化和根目录边界检查，拒绝路径穿越、符号链接逃逸和用户提供的绝对路径。
- `/api/photos/:id` 每次检查归属后返回图片；不因为知道 ID 或文件哈希就获得读取权限。不使用公共永久直链，也不从任意外部 URL 下载用户提供的图片。
- 文件先落盘、校验、原子重命名，再提交元数据；失败只留下可追踪的保留文件。用户未确认时不自动清理文件或历史记录。

## AI 与费用边界

DeepSeek 只处理用户主动请求的餐食文字/图片分析。认证改由自托管会话完成；数据库事务预留每日预算，并通过请求 ID 幂等保存结果与用量。现有自动统计、计划、恢复判断和复盘不调用模型。模型服务密钥只在服务器配置，不提供自动 OpenAI 备用。

默认本地模式保持付费接口关闭。显式 `preview:coach:ai` 仅用于回环地址验收，以进程内限额替代生产预算；它不具备账号隔离，不能部署到公网。ChatGPT 深度分析由用户主动发起，不作为定时后台调用。Google 同步和 MCP 继续采用显式授权、最小摘要、凭证加密/散列和随时撤销。

## 迁移和恢复流程

1. 先导出当前完整 ZIP，核对清单、记录数量及真实照片哈希；保留原始文件，不清空源浏览器或旧库。
2. 在全新本地/测试 PostgreSQL 和空的受限文件卷中导入，按新账号映射旧 ID，校验照片关联。旧来源不可访问的图片必须明确报告缺失，不能假装恢复成功。
3. 新后端实现后，至少验证两台设备的登录、记录、冲突、图片鉴权和 ZIP 往返；完成容量与恢复中断演练。
4. 服务器级备份同时覆盖 PostgreSQL、一致性照片清单和文件卷；凭证使用单独加密备份渠道，不能塞进用户 ZIP。恢复先暂存、校验并自动备份现状，用户确认后才事务切换。
5. 用户验收后再讨论生产环境。旧数据保持只读可恢复，切换和回滚都需明确确认，绝不把测试库覆盖到正式数据。
